# CompelOS qualification engine

The local qualification pipeline is SerpAPI Finder → PostgreSQL CRM/queue → the owner's signed-in LinkedIn browser session with targeted Voyager reads → bounded public website research → deterministic qualification → PostgreSQL CRM. The dashboard is Next.js. `worker.cjs` hosts one persistent agent in `src/lib/compel-agent.cjs`; the former supervisor script is only a compatibility entry point.

## Non-negotiable rules

- The current user-authorized policy is 300 unique person profiles per account per local day plus a minimum 60 seconds between profile starts per account. This explicitly supersedes the original daily-cap-only instruction. The existing `daily_limit` remains editable; `DEFAULT_DAILY_SCRAPE_LIMIT` defaults to 300. PostgreSQL atomically reserves both the profile slot and `next_profile_at` immediately before the first profile-data read (including a profile fallback retry). Same-day retries use no additional daily slot but obey the interval; cached captures/session checks are free. Do not add other permits, hourly/rolling caps, per-kind budgets, cooldowns, jitter or throttle sleeps. Per-kind counts remain statistics only.
- Stop an account on LinkedIn/LICDN HTTP 401/403/429/999, login/authwall/checkpoint/challenge, a security warning, or mismatched account identity. Preserve the exact reason until the human reviews the account. A settings save, process restart or stale callback cannot clear a hold. Manual sign-in alone confirms the intended member and leaves processing paused.
- On 2026-10-26 the user explicitly authorized restoring the older Puppeteer-extra/stealth and Voyager approach. This supersedes the original rendered-profile-only/no-private-endpoints/no-stealth instruction. Retain the installed Puppeteer version and pinned full Chrome for Testing. Account browsers use isolated `puppeteer-extra`/stealth instances; the public renderer uses plain Puppeteer. Confirm the signed-in member from the rendered feed, then read only the requested member’s declared Voyager profile/activity/contact collections through that browser’s existing session. Never substitute unrelated included members or infer missing evidence. Keep bounded requests, checkpoints and reactive stops; no rendered-profile fallback that silently doubles work. Processing is headless; explicit manual sign-in/review opens the same persistent profile visibly after closing the previous owned browser. Never run both modes on the profile simultaneously. No password entry, session-cookie export/logging, proxies or additional fingerprint workarounds. Ask before changing browser libraries. Local fixtures do not prove live endpoint compatibility or protection from account restrictions.
- PostgreSQL is the only runtime queue and state store. Keep owner-fenced leases, checkpoints, canonical-profile duplicate protection and suppression/contact-history guarantees. No Redis, BullMQ, Docker or service split. Local PID/launch/browser-ownership files are OS diagnostics, never an alternate queue.
- The user explicitly requires all eligible started accounts to process simultaneously. Use one headless LinkedIn browser and one sequential tab per account, each with its own persistent profile, lease, daily allowance and one-minute interval. The default browser ceiling is 10 (the account limit), with `MAX_ACTIVE_BROWSERS` retained as an explicit optional lower ceiling. A positive legacy `active_count` enables all available accounts; zero pauses globally. Connecting/settings saves still never authorize processing. Keep an 8 GB Windows machine bounded: one agent, two shared public research tasks, three shared HTTP requests and a shared six-item result/checkpoint save queue with account-local error recovery. Public rendering uses a separate short-lived headless Chrome. Recycle/idle-close only the relevant account browser while retaining sign-in and intent; a manual request with spare capacity must not recycle unrelated accounts.
- Recover a stale owner only after its PID is confirmed dead and its heartbeat expires, or after a verifiable explicit release. Unknown ownership must produce a useful failure; never erase an unverified/live Chrome lock or user profile.
- Followers must be strictly greater than `MIN_FOLLOWERS` (default 500). Read the raw value and parsed count from the identity-matched profile response, immediately after identity and before activity/contact/website work. Keep connections separate. At/below threshold → REJECTED/FOLLOWERS_BELOW_MIN; absent/unparseable → REVIEW. Never guess from connections. Store the applied threshold with the evidence. Legacy qualified records stay follower-unchecked until explicitly selected for recheck; never automatically requeue them.
- Finder accepts only explicitly evidenced person residence in UK, US or Canada matching the requested country. Search targets, headlines, clients, employers and LinkedIn subdomains never prove residence. Save raw country evidence separately from query provenance; reject missing, ambiguous, foreign or conflicting discovery evidence before import. Main CRM qualification checks the identity-matched Voyager profile location: confirmed foreign residence rejects before downstream work; unknown residence requires REVIEW. Keep this gate in full/compact CRM projections and resumed checkpoints. Never guess a country from a city alone or mass-relabel legacy discovery locations.
- Once a lead is decided, skip remaining page actions/crawls. Resume partial work from PostgreSQL checkpoints. A website/CRM failure must not reread LinkedIn. Nonretryable failures are terminal REVIEW with evidence, not a retry loop.
- Worker launch/control features are unavailable on Vercel. Keep the local-host/admin and same-origin checks. Never inspect, edit, stage or commit real secrets or `.env` files. Runtime configuration loading is allowed; `.env.example` may document requested public variable names/defaults.
- Ask before deleting user data or destructive schema changes. Additive migrations are allowed. Do not reset or include unrelated work in a commit.

## Verification and documentation

Read [engine-v2.md](docs/engine-v2.md), [engine-audit.md](docs/engine-audit.md), [engine-measurements.md](docs/engine-measurements.md), [finder-review-audit.md](docs/finder-review-audit.md) [engine-parallel-accounts.md](docs/engine-parallel-accounts.md) and [engine-voyager-restore.md](docs/engine-voyager-restore.md). Browser recycling defaults to 50 captured jobs, still subject to the existing process-tree memory guard and idle closure; it never stops the queue at 50. Before behavior changes, preserve up to 50 already-decided CRM records with reasons/evidence. Replay stored evidence after every phase without visiting LinkedIn; report every decision delta and distinguish requested follower/location changes and uncertainty-routing corrections from unexpected drift. Keep private snapshots and full per-lead reports under ignored `data/engine-v2/`; PostgreSQL stores benchmark manifests and reports. One-time stored-evidence policy repairs retain before/after assessments in `compel_qualification_repairs`, use compare-and-swap fences, preserve contact/suppression/manual evidence, and never enable processing or clear review holds.

Work and commit phase by phase. Validate the affected behavior with meaningful tests. Engine checks: `node --test --test-concurrency=1 tests/workers/*.test.cjs tests/prospects/*.test.cjs tests/coach-prospecting/*.test.cjs`; CRM checks: `npm run test:crm`; types: `npx tsc --noEmit`; lint: `npm run lint`. Browser tests use local fixtures, never live LinkedIn. Run authorized live measurements separately from tests/builds, reuse the same 30 profile URLs, preserve review holds and disclose failed/partial measurements. Do not infer performance gains from an uncompleted batch.
