## Architecture

`npm run worker` starts one persistent Node agent (`worker.cjs` → `src/lib/compel-agent.cjs`) with a shared five-connection pool. The existing worker entry point keeps desktop commands and deployment guards compatible while lifecycle logic lives in the agent module. No supervisor/account/public-research child Node processes remain. The old supervisor command is a compatibility launcher for the same agent.

Every eligible started account has its own concurrent capture lane: one sequential Puppeteer-extra/stealth tab in its own persistent account browser/profile. The default browser ceiling is 10, matching the maximum account count; it creates browsers only for actual requested work. `MAX_ACTIVE_BROWSERS` can deliberately lower that ceiling. A slow account does not serialize the others. The pinned full Chrome for Testing runs headless for processing and visibly for explicitly requested manual sign-in/review, reusing the same saved profile after a verified close. Each lane claims a distinct PostgreSQL job and verifies its saved account identity only when a browser is needed. The saved account identity is confirmed from the rendered feed. The reused feed tab then makes targeted Voyager GETs for the requested member. Identity-matched location and followers stop ineligible leads before activity/contact reads. Missing/unparseable followers require REVIEW. A dated matching-author activity record is required for the main CRM. Inactive/unknown activity stops before contact and website work when the main CRM policy requires recent activity. Coach prospecting retains its original business criteria and does not inherit that email/activity gate. Active candidates continue to the targeted contact response and remaining public evidence. There is no per-lead rendered profile/activity/contact navigation. The public renderer stays on plain Puppeteer.

Checkpoint/result saves from all account lanes share one bounded serial queue (capacity six). Account scopes retain separate errors, drains and recovery; closing/recovering one scope does not close or clear another. Each account's next capture claim waits until its own profile interval permits it; no next-lead lock is held during that gap. Capture lanes never wait for public website research. Database admission applies backpressure when the shared save queue is full. Daily reservations and ownership checks remain synchronous because their atomic guarantees must precede browser actions. Ordered saves prevent an earlier checkpoint from overwriting a later handoff. Complete captures transfer to the shared public lane under the same job ID and release the account claim.

Two public tasks share three HTTP slots, use fetch + Cheerio and a PostgreSQL cache with eight bounded slots per domain, 256 KiB per slot and a 24-hour TTL. Qualification rechecks email attribution per person even when HTML is cached. Home/contact/about routes receive priority; only observed links are followed. Defaults: eight distinct routes, twelve total attempts, twenty seconds across the site's wall-clock lifetime, five seconds per request. Stop when the existing qualification questions have enough evidence. Nonretryable HTTP failures do not trigger rendering. A successful but unreadable HTML shell gets one bounded rendering attempt in a separate on-demand headless Chrome; still-unreadable evidence becomes REVIEW. Transient website/CRM failures resume stored evidence within bounded attempts, without a LinkedIn visit or an added retry sleep.

The existing capture/research queue indexes were sufficient in the measured EXPLAIN plan. No speculative queue index was added. Account statistics are batched by action kind. Saves preserve do-not-contact flags, contacted history and email verification; replacing an email invalidates its prior verification.

## Daily cap and followers

The existing database column is `compel_linkedin_accounts.daily_limit` (the daily profile limit; no duplicate limit field was introduced). Its existing 1–400 constraint remains. Account settings show used/limit and let the operator edit it. New-account defaults use `DEFAULT_DAILY_SCRAPE_LIMIT` (300).

`compel_worker_account_profiles` has an account/date/canonical-URL primary key. An account-row lock serializes the count and insertion immediately before the first requested member-profile read. Same-day retries and return visits use no extra daily slot, but obey the interval when they reread profile data. Another account has its own count. Claims, cached captures, source lists and session checks consume no profile slot. The configured PostgreSQL day uses `DAILY_LIMIT_TIMEZONE`, defaulting to the worker machine's IANA time zone at startup. The next midnight is computed by PostgreSQL, including DST. At the cap, intent stays enabled and status becomes DAILY_LIMIT_REACHED with the resume time; already-captured public work finishes. Notifications or the idle poll notice a limit edit/new day.

Followers must be strictly greater than `MIN_FOLLOWERS` (500). The identity-matched profile response provides the raw value and an integer, supporting grouping, K/M suffixes and tested localized labels, including Arabic bidi text. Connections have separate evidence and never substitute for followers. At/below threshold → REJECTED with FOLLOWERS_BELOW_MIN; absent/unparseable → REVIEW. Evidence includes the applied threshold so a dashboard with different environment defaults cannot reinterpret the saved check. A new or resumed worker decision uses the current threshold without repeating website work. A completed old follower-only stop cannot substitute for the downstream capture newly eligible profiles still need.

`QUALIFICATION_VERSION` is 3; research schema version 1 remains compatible. Current main CRM captures also require evidenced UK/US/Canada residence from the identity-matched profile response. A confirmed foreign country rejects immediately; unknown location requires REVIEW after the follower check. Full and compact CRM evidence retain the gate. Existing legacy follower-unchecked records are not automatically requeued; proven foreign-country records can be corrected from stored identity-matched evidence. Select CRM rows and use **Recheck followers** to request fresh full qualification. This bypasses completed-today deduplication only for the selected request, keeps active-profile duplicate protection and consumes the account's daily slot only if it has not already read that profile that day. Followers/connection evidence is expandable in the CRM and prospect evidence view. The audit and bounded policy refreshes are documented in [finder-review-audit.md](finder-review-audit.md).

## Start, pause and recovery

Use Start workers in the local dashboard or `npm run worker`. Connect/Open session opens the saved profile for manual sign-in. Start/Resume authorizes all eligible selected accounts to process simultaneously until their own Pause, disable, sign-out, daily cap or account review. The legacy database `active_count` now represents the global allow/pause switch: zero disables processing; any positive legacy value enables all available accounts. Settings expose/persist the enabled count while allowed, so old saved `1` values cannot silently hide the other accounts. A settings save still never starts an account. Restarting the agent resumes saved intent and unfinished PostgreSQL checkpoints. A manually paused or held account stays paused/held. `npm run worker:stop` requests a graceful PostgreSQL stop without clearing intent or evidence. See [Windows sign-in startup](windows-agent.md) for the optional Task Scheduler setup.

Account startup displays REQUEST_RECEIVED → AGENT_ACK → BROWSER_STARTING → SESSION_VERIFIED → PROCESSING. Failures include the stage, exact reason and recovery action. Startup history retains intermediate stages even if browser startup finishes between dashboard polls. The local launch marker exposes errors before the database is reachable. A live/unverified PID prevents a second agent; a confirmed-dead owner waits for heartbeat expiry. A legacy explicit release is recognized by its lease/updated timestamp fence, even when its final browser snapshot says BROWSER_CLOSED.

The agent registry records host/PID/script ownership. Only confirmed-dead, expired owners have processing claims reset to pending; checkpoints and security holds remain. Lease expiry alone never steals work from an unknown/live process. Chrome Singleton files are removed only with verifiable dead ownership/expired heartbeat or a verified close. A live or unverified Chrome profile remains blocked with an action to review its owner. Profiles/cookies and user data are never cleared or moved automatically.

Browser crashes and transient Voyager transport failures resume the current checkpoint within two retries; exhausted attempts become REVIEW. A transport failure retains the browser and skips already captured profile/contact stages. Initial browser startup retries within three attempts and then shows FAILED. Resource recycling closes that account's Chrome after fifty captured jobs, above a sampled 1536 MiB browser-tree threshold, or after 30 seconds idle, and later reopens the same saved profile. There is no 50-job stop. A manual request only yields another browser when the explicit browser ceiling is full; spare capacity leaves unrelated lanes running. Public Chrome closes after 15 seconds idle. Idle polling backs off from 2 to 30 seconds; PostgreSQL NOTIFY wakes new commands/jobs. The explicit 60-second profile interval is the only pacing rule and applies independently per account. A waiting profile interval keeps that account's Chrome alive rather than recycling it after the shorter idle timeout. Account leases renew independently before statistics admission, so a slow account save cannot delay its siblings' heartbeats. Other waits are idle/resource/recovery waits. Rendering waits use DOM/navigation events.

Reactive stops cover LinkedIn/LICDN HTTP 401/403/429/999, authwall/login/checkpoint/challenge, security warnings and mismatched identities. They immediately block further account actions, persist the reason and show the window for manual review. Settings changes/restarts cannot clear them. The user-authorized Voyager reader uses private endpoints through the saved browser session. No password entry, cookie export or browser-library migration was introduced. Worker features are unavailable on Vercel.

## Configuration

| Variable | Default | Purpose |
| --- | --- | --- |
| `MIN_FOLLOWERS` | 500 | Require a strictly greater follower count |
| `DEFAULT_DAILY_SCRAPE_LIMIT` | 300 | Default for new accounts; existing database values win |
| `DAILY_LIMIT_TIMEZONE` | worker local IANA zone | Day boundary stored in PostgreSQL |
| `MAX_ACTIVE_BROWSERS` | 10 | Maximum concurrent LinkedIn browsers; one per eligible started account |
| `CHROME_RECYCLE_JOBS` | 50 | Automatic Chrome recycling, never a manual job stop |
| `CHROME_RECYCLE_RSS_MB` | 1536 | Sampled whole-browser-tree recycling threshold |
| `LINKEDIN_BROWSER_IDLE_MS` | 30000 | Close idle LinkedIn Chrome, retaining profile |
| `PUBLIC_BROWSER_IDLE_MS` | 15000 | Close idle public headless Chrome |
| `WEBSITE_MAX_PAGES` | 8 | Distinct site route budget |
| `WEBSITE_MAX_ATTEMPTS` | 12 | Total site attempts across resumes |
| `WEBSITE_MAX_MS` | 20000 | Site wall-clock deadline across resumes |
| `WEBSITE_REQUEST_TIMEOUT_MS` | 5000 | Individual HTTP deadline |
| `WORKER_PROFILE_ROOT` | local app-state directory | New profiles only; existing `.browser-profiles` wins |
| `WORKER_LAUNCH_DISABLED` | unset | Disable the dashboard's process launcher |

The npm worker command limits the Node heap to 384 MiB. The resource panel measures the agent plus its whole Chrome process tree, not just Node RSS. RSS sums shared pages conservatively; CPU uses 100% per core. Fifteen-second sampling can miss short-lived peaks. The quiet-queue query rate is the comparable idle figure; during active work, outside-trace maintenance queries are also counted. Private raw evidence and reports stay in ignored `data/engine-v2/`; benchmark manifests/reports also live in PostgreSQL.

## Removed paths and checks

Removed: per-account child supervisor, separate public-research process, automatic folder queue/result import and unused file-based progress writer/resume path, unused hourly/rolling/schedule policy module, expiring one-hour processing authorization, fixed rendering sleeps, per-kind permits and check budgets, and post-decision automatic website continuations. Existing database columns/legacy data remain for compatibility; no destructive migration ran. Finder progress still reads `queue-results`, so that consumer/directory and all user files remain.

Run engine/CRM tests, TypeScript and lint as listed in root AGENTS.md. Regression snapshots replay stored evidence without LinkedIn. The exact before/after measurements, deliberate follower changes, startup failure and remaining LinkedIn page-load floor are recorded in [engine-measurements.md](engine-measurements.md).

Production builds exclude local profiles, environment files, queues, private evidence and other runtime directories from file tracing. The Finder/Create dynamic-path warnings can still appear; run `npm run build` and then `node scripts/engine-verify-build.cjs` to verify the emitted route manifests contain zero private runtime entries. These packaging exclusions do not delete runtime files. Worker process launch/control remains disabled on Vercel.

Profile starts also reserve `compel_linkedin_accounts.next_profile_at` atomically in PostgreSQL. Restarting or reusing an already-read profile cannot skip the 60-second interval. Cached captures and public research continue without a fresh profile start; a pause or review hold prevents the next start.
